# Review: dex-tracker, the Vite entries and the session measurement (2026-10-31)

Scope: everything between `origin/master` and `92b6849`. That covers the dex-tracker scenario
(spec, API, data, tests, gold app), `bench/flow.mjs` and the measurement changes, the
report changes, and the React, Preact and Lit + Vite entries. The question I tried to answer
is what a skeptical reader would say after
`node bench/run.mjs --scenario=dex-tracker --frameworks=all --iterations=5 --effort=high`.

Nothing in the repo was changed except this file. Every "verified" below was checked by
running something: the pilot apps re-measured with an instrumented copy of the flow, the
test suite run against the gold app, small test apps of my own, or the API queried with and
without the overlay. The rest is marked as a suspicion.

## Summary

The measurement code is sound where it counts most. Soft-navigation LCP really is timed
from the tap, 4x CPU throttling holds across full page loads, and the hard and soft clocks
line up. The problems are in what gets measured and in tests that the new Vite entries will
trip over.

Fix before the 45 to 50 hour run:

1. **The headline LCP often isn't the data.** On `/`, `/needs` (in the gold app), `/trades`
   and `/trades?page=2`, the LCP element is the static `h1`. An app that paints its heading
   before fetching gets a near-zero "click LCP": 16 ms against roughly 770 ms for the same app
   fetching first. Whether a framework wins the headline then depends on its loading-state
   habits and CSS. (M1)
2. **Several tests fail any app that fetches in the browser**, because they read option
   lists and table rows once, right after `load`, without retrying. React, Preact, Lit and
   vanilla with Vite are exactly the apps that fetch in the browser. Their agents will be pushed into SSR or
   hacks to pass. (T1)
3. **One failed click in any of the 5 sessions loses the whole iteration's measurement**,
   Lighthouse results and line counts included. (B1)
4. **The live-data overlay leaves most detail pages unchanged**, so an app that prerenders
   `/pokemon/*`, `/games/*` or `/friends/*` at build time passes the tests and is then
   measured on a static page. One of the Lighthouse URLs is `/pokemon/slowpoke`, which the
   overlay doesn't touch. (T2)

Then the methodology questions, which won't crash anything but will shape the conclusions:

5. With 562.5 ms added to every request, warm connections included, the click numbers mostly
   count round trips. That makes the 2-round-trip designs (Next's RSC payload then a route
   chunk) look 3.75 times worse than slow 4G would. (M2)
6. As written, the app and flow give an SPA no way to win a click. Every page needs fresh data
   from the server, MPA documents are 2 to 5 KB, and the flow never revisits a page or filters
   loaded data. In the pilots the Astro MPA won every step. That may be the real answer, but
   the README says this scenario was "built to be the kind of app SPA frameworks are made for".
   (M3)
7. The headline is one click on one link, but the claim being tested ("the second click pays
   for the first") is about a whole session. (M4)

## How the pilots actually behave

I re-ran the three pilot apps from `runs/pilot-20261030-dex-tracker/` through the same session as
`flow.mjs`, with the web-vitals attribution build and a CDP log of every request. The script
is `probe.mjs` in this session's scratchpad. These are single sessions, so the numbers are
approximate.

| Step | Astro (MPA) | SvelteKit | Next.js |
| --- | --- | --- | --- |
| `/` cold load, LCP element | `h1` "Overview", 1,288 ms | `h1` "Overview", 1,484 ms | `h1` "Overview", 1,216 ms |
| Needs click, LCP element | "Wild in" cell (9,520 px²), 720 ms, hard | "Wild in" cell (18,414 px²), 752 ms, soft | "Wild in" cell (17,490 px²), 1,256 ms, soft |
| Pokémon click | artwork PNG, 2,304 ms | artwork PNG, 2,318 ms | artwork PNG, 2,305 ms |
| Trades click | `h1` "Trades", 716 ms | `h1` "Trades", 728 ms | `h1` "Trades", 698 ms |
| Next page | `h1` "Trades", 692 ms | a 1,482 px² cell, 695 ms | a 1,482 px² cell, 686 ms |

Other things these runs showed:

- Soft-navigation start time minus the `pointerdown` time was 0.0 to 0.2 ms on every soft step. So the soft and hard
  clocks agree. That was the thing I most expected to be wrong, and it isn't.
- A 20-million-iteration busy loop took about 60 ms in every document of the Astro session,
  so CPU throttling survives hard navigations.
- Astro's hard navigations fetch a 2 to 5 KB document and get the CSS from the memory cache
  (`immutable`). There isn't much left for an SPA to save.

## Methodology

### M1. LCP doesn't reliably mean "the data is on screen" (high)

LCP picks the largest text block or image. On these pages that is usually the `h1`:

- `/`: the charts are SVG, which LCP ignores, and the summary values and activity items are
  smaller than the `h1`. All three pilots report `h1` "Overview".
- `/needs`: depends on CSS. In the pilots, the "Wild in" cell is wider than the `h1`, so the
  data counts. In the gold app it isn't, and the LCP is `h1` "Needs" (3,690 px²). Agents copy
  the gold app's screenshots, so many apps will be like the gold app.
- `/trades`: `h1` in all three pilots. `/trades?page=2`: the `h1` for the MPA, a small cell for
  the SPAs, because a soft navigation only counts elements it repaints.

Soft-navigation LCP only counts new paints after the click. So an app that pushes the URL,
paints the heading and a "Loading…" line, then fetches, gets credit for the heading. The
spec/tests reviewer measured this with `runFlow` itself:

| App | Needs click LCP |
| --- | --- |
| Gold app (MPA) | ~1,299 ms |
| Test SPA: paints `h1` + "Loading…", then fetches | 16 to 17 ms |
| Test SPA: fetches, then `pushState` and render | ~772 ms |

The same goes for cold loads. A client-rendered app's `/` LCP is the moment its bundle runs
and paints `<h1>Overview</h1>`, not when the dashboard fills in. SSR with streaming and
`loading.tsx` or `Suspense` boundaries lands in the same place.

So the headline depends on whether the agent happened to add a loading state, and on CSS
widths. That 750 ms swing is bigger than any framework difference the pilots showed.

Options, smallest first:

- **Record the LCP element.** Switch `flow.mjs` to `web-vitals.attribution.iife.js` and store
  `attribution.target` per step. This is one line, and without it nobody can audit the
  numbers. It also tells you after the fact which iterations measured the data.
- **Time a data element as well.** In the init script, a MutationObserver puts
  `elementtiming` on a known data element as it's inserted. For Needs that's the first row's
  Pokémon link in "Needed species", or the "N species needed" text. Report click to its
  render time next to LCP, or instead of it. This is still Chrome's own paint timing, not a
  harness timer, and it works the same for hard and soft navigations, through the
  `timeOrigin` arithmetic the hard path already uses.
- At the very least, say in the report that the LCP on these pages is the heading.

### M2. The throttling turns clicks into round-trip counts (medium-high)

Lighthouse's DevTools preset adds `requestLatencyMs: 562.5` (150 ms RTT × 3.75) to *every*
request. The 3.75 factor is meant to stand in for DNS, TCP, TLS and slow start on a cold
page load. On a click, the connection to `app.localhost` is already warm, so the real cost of
one request on slow 4G is about 150 ms, not 562.5. Meanwhile a browser opening its *first*
connection to `api.localhost` during a click pays nothing extra for the handshake, which is
wrong the other way.

Look at the pilot clicks with that in mind. Every one is 1 round trip (about 590 ms) plus 50
to 150 ms, except Next's Needs click, which is 2. Differences in CPU and bytes, where SPAs and
MPAs actually differ, are small next to that floor. The number of sequential requests
dominates, and each extra request costs 3.75 times what it would on a real slow-4G phone.
Next's 1,250 ms against SvelteKit's 750 ms on the headline click is mostly this.

This doesn't make the cold loads wrong. They're consistent with Lighthouse's own DevTools
mode, and the README is clear that this breaks comparability with pokedex. The README's line
"it does so the same way for every app" is the part I'd push back on: the error grows with the
number of sequential requests, so it isn't the same for every architecture.

Options:

- Keep it and say plainly in the report that a click costs about 590 ms per sequential round trip
  under this model, so the click column is roughly "how many round trips". Adding a
  per-step count of sequential requests on the critical path would make that visible.
- Or throttle clicks at `latency: 150` (call `Network.emulateNetworkConditions` again after
  the cold load). It's a two-line change, but it is a second model to explain.
- Packet-level shaping (`tc netem` on the measurement container's loopback, or a userland
  throttling proxy) gets connection setup and multiplexing right, but it's real work and
  needs `NET_ADMIN`. I wouldn't do it before this run.

### M3. SPAs can't win a click in this flow (medium, a scoping question)

As written, every measured click needs at least one round trip for every architecture,
because the data is live and no page is revisited:

- The MPA documents are tiny: Astro's `/needs` is 3.5 KB compressed and its CSS comes from
  the memory cache. An SPA saves almost nothing by not reloading the page.
- The flow never repeats a request an SPA could have cached. The only data shared between
  steps is `/api/meta` and the friends list, between `/trades` and page 2.
- Browser API calls cost about 592 ms each, against about 30 ms from the server, so
  client-fetching SPAs pay the most per call.
- Prefetching evens things out, and anyone can do it. I checked a static page with one
  `<script type="speculationrules">`: its click went from 617 ms to 45 ms. Prerender attempts
  fall back to prefetch in Playwright's Chromium, `deliveryType: navigational-prefetch`.
  Next's viewport prefetch and Astro's `prefetch` do the same thing. That's fine as a
  finding, but the report should say which apps prefetched. Otherwise "framework X has a
  fast second click" really means "framework X prefetches links by default".

Pilot session totals (cold load plus four clicks): Astro 5.4 s, SvelteKit 5.8 s, Next 6.2 s.
The MPA won every step.

If that's the answer, it's a good result and worth publishing. But if the aim is to give SPAs
their best case, the flow needs at least one step where client state can pay off:

- Go back to a page already visited (Needs → Pokémon → Needs). SPAs with a cache are
  instant; MPAs get bfcache. Both are realistic, and nothing has to be typed.
- Change a `/needs` filter. This needs real keyboard or pointer input, not `selectOption`,
  for Chrome to treat it as a soft navigation. Check that first.
- Click "Show more" on the overview, which appends items without changing the URL. LCP won't
  measure that, so it would need the `elementtiming` approach from M1.

### M4. One click is a fragile headline (medium)

The claim being tested is "the second click pays for the first", and that's about a session
total. One click on one link mostly measures whether the Needs route needed a lazy chunk. Code-splitting SPAs pay the most on the first visit to a route, so a single click is their worst case.
Later clicks are cheaper (Next: 1,250 ms on Needs, about 700 ms on the rest).

Suggestions:

- Add a "session total" column, cold load plus all clicks, or the median of the clicks next to
  the first click. Those numbers are already in `results.json`.
- Drop the Pokémon step from any total, or replace it. Its LCP is a 126 to 203 KB PNG from
  `/media` at 1.4 Mbps: 2,280 to 2,320 ms in all three pilots. That's bandwidth, not
  framework. Frameworks with an image optimizer (`next/image`, `@nuxt/image`) can shrink it,
  which may be worth measuring in its own right, but then it should be called that. Also, the
  species clicked comes from the Needs table, so it is never caught. The page always shows its
  lighter "Not caught yet" variant.
- Show the spread across iterations (min to max, or each iteration) for the flow columns. Within one
  app the 5 sessions agree to ±5 ms, because the throttling is deterministic. All the variance
  is in which architecture the agent chose, and a median of 5 hides a 2-out-of-5 minority.

### M5. Clicking after 1.5 s of network idle favors prefetchers (low, document it)

`settle()` waits for 1.5 s of network quiet before every click. Prefetchers get a free head
start that a fast-clicking user wouldn't give them. That's a defensible choice, but the README
should say so. It also moves bytes between steps (see B2).

### M6. SvelteKit pays a tax that the decision doc says shouldn't be measured (medium)

`docs/decisions/2026-10-31-plain-http-tests.md` keeps the tests on plain HTTP, because getting
a framework to agree with its proxy about the protocol is "a day-one setup problem a team solves once, not
something to measure". But option 1 means SvelteKit agents solve it in *every* run, and the
pilot spent most of its 83 minutes on it. That is measured, as SvelteKit's time and cost.
Option 2, the tests behind the same Caddy proxy, is the one that matches the stated principle.
It would also catch Astro and Qwik apps that silently reject form posts behind the proxy.
It's about 25 lines, and Caddy moves into the base image. If you keep option 1, the report has
to flag SvelteKit's time and cost as inflated by the harness, not by the framework.

### M7. The `/trades` page forces a waterfall on browser-side apps (medium)

The Friend filter lists every friend: 150, or 151 with the overlay. But `/api/friends` caps
`pageSize` at 100 (`api/server.mjs:123`). The app has to fetch page 1, read `totalPages`, then
fetch page 2. The gold app does this (`gold/server.mjs:53`). On the server that's an extra 30 ms. In the
browser it's an extra 592 ms on a measured step. Nothing about the frameworks causes it; it
comes from an arbitrary cap. Raise the cap to 200, or add the friends to `/api/meta`.

## Harness bugs

### B1. One failed click loses the iteration's whole measurement (high, verified by reading)

`measureFlow()` doesn't catch anything. `results.json` is only written after Lighthouse, the
flow and `codeStats()` all succeed (`measure.mjs:204-216`). If one click in any of the 5
sessions times out, the iteration gets no numbers at all: no Lighthouse, no line counts.

That's likely to happen at least once across 75 apps. The tests click at 1280 px; the flow
clicks at 412 px. An app with a hamburger menu, or cards instead of the table on mobile,
passes every test and then times out in the flow. A URL mismatch also throws, for example a
redirect from `/needs` to `/needs/`.

Fix: catch per session, record `{ type: 'error', error }` for the step, and keep going. Write
`results.json` in a `finally`.

### B2. Bytes and requests per step are wrong (medium, verified)

`flow.mjs` counts a request only on `Network.loadingFinished`. Two problems:

- SvelteKit's `__data.json` and Next's `?_rsc` responses finish with `net::ERR_ABORTED`
  (canceled) once the framework has read them, so they're never counted. That's why the
  pilot's SvelteKit "Next page" step reports 0 requests and 0 bytes while still taking one
  round trip. The click's own data never shows up in "First click transfer".
- Prefetches land in whichever step was running when they fired. Next's Needs step includes
  RSC prefetches of `/games/*` and `/pokemon/*` for the links in the table, and its home step
  includes the prefetch of Needs.

The "First click transfer (KiB)" column is therefore wrong for at least SvelteKit and Next.
Count requests on `requestWillBeSent` and bytes from `Network.dataReceived`
(`encodedDataLength`), or drop the column. Dropping it is simpler, and nothing in the
headline depends on it.

### B3. Sessions where the click wasn't detected vanish from the median (medium)

`median()` drops `null`s. If 3 of 5 sessions come back `none`, the step's LCP is the median of
the other 2, and the type column just says `soft/none`. Record how many sessions produced a
number, and treat fewer than all 5 as a failure in the report rather than a number.

### B4. A step that never settles is silent (low)

`settle()` gives up after 30 s and returns as if all were well. An app that keeps a long poll,
an SSE stream or a retry loop open costs 30 s per step, and nothing records it. Return a flag and
store it in the step.

### B5. Prerender would break the hard-navigation math (low, latent)

If a prerendered page is ever activated, `performance.timeOrigin` is when the prerender began,
before the click. web-vitals reports LCP from `activationStart`, so `lcp + gap` comes out wrong
or negative. It doesn't happen today: Playwright's Chromium falls back to prefetch (verified).
Send `activationStart` with each vital and add it back, so a Chromium update can't silently
break this.

### B6. Throttling only applies to the page's own target (low, suspicion)

`Network.emulateNetworkConditions` and `Network.enable` are only sent to the page's CDP
session. Fetches made by service workers or dedicated workers are probably neither throttled
nor counted. Qwik 1.x registers a prefetch service worker by default. Worth a quick check on a
Qwik app. If true, either set the conditions on auto-attached targets or note it.

### B7. Smaller things

- `warm()` doesn't include the Pokémon page the flow clicks (`/pokemon/ivysaur`, fixed by the
  data). Server caches are cold for it in session 1 only.
- The flow doesn't record the Chrome version or Lighthouse's `benchmarkIndex`. CPU throttling is
  a multiplier on the host's speed, so results from different machines aren't comparable without them.
- There are now two cold-load LCPs for `/`, the flow's and Lighthouse's. Both use the same
  throttling, and in the pilots they agree within 20 ms. Fine, but the report should name
  one as the headline and treat the other as secondary.
- INP and CLS are collected and never reported. That's harmless, or you could drop them from the init script.

## Tests and spec

### T1. Tests that don't retry fail apps that fetch in the browser (high, verified)

`page.goto` waits for `load`. Then these read the DOM once:

- `lists.spec.mjs:44-46, 106-108, 168-172, 233-234`: option lists from `/api/meta` and the
  friends list.
- `details.spec.mjs:125`: `(await rows(...))[0][0]` throws a TypeError on an empty table.
- `writes.spec.mjs:13-16, 45`.
- `details.spec.mjs:14`, if the app renders the table header before the rows.

A minimal client-rendered page, run against the real `helpers.mjs`, got 0 options and 0 rows. It
failed even when the module script used a top-level `await` on the fetch. The gold app and all
three pilots render on the server, which is why nobody saw it.

This hits the three new Vite entries, plus Angular without SSR and anything with
`ssr: false`. Their agents won't fail. They'll spend tokens finding a way around it, by
adding SSR or delaying `load`, and the benchmark will then measure the workaround.

Fix: an `expectOptions()` helper built on `expect.poll`, and
`expect.poll(async () => (await rows(t))[0]?.[0])` instead of indexing.

### T2. The live-data overlay doesn't reach most detail pages (high, verified)

`tests/fixtures/live-data.sql` adds one friend, one trade and one catch of the lowest needed
species (Bulbasaur's line: `ivysaur`), and bumps active hunts. I compared API responses with
and without the overlay, ignoring the port in media URLs. These are byte-identical:
`/api/species/slowpoke`, `/api/friends/8`, `/api/games/blue`. The API reviewer adds
`species/eevee`, `games/blue/dex`, `games/red`, `trades/1`, completed hunts,
`stats/completion-by-game` and `catches?shiny=true`. `/api/friends/1` and
`/api/species/ivysaur` do change, but no test checks them.

So an app that prerenders `/pokemon/*`, `/games/*` and `/friends/*` passes, against the spec.
Static output is Astro's default, and Next has `generateStaticParams`. Lighthouse's
`/pokemon/slowpoke` and `/friends/1` are then served as static files.

Fix: a few more lines in the overlay. Add a catch of Slowpoke and of Eevee dated `today`, a trade with
friends 1 and 8, and a catch in Blue. The tests already compare against the live API, so no
test code changes.

### T3. Passing the navigation tests doesn't mean the flow can measure the app (medium)

- The tests use a desktop viewport; the flow uses 412 px mobile (see B1).
- `expectNavigation` clicks right after the page becomes visible, which may be before
  hydration. A server-rendered app can pass as "new document" there, and then in the flow,
  after 1.5 s idle, do a client-side navigation that Chrome doesn't detect. The README's "no
  app can end up with no number" overstates what's checked.
- The flow clicks `row.nth(1)…getByRole('link').first()`; the test clicks by name. The
  Trades click from a Pokémon page isn't tested.

Fix: run the navigation tests at the flow's mobile viewport with the flow's own locators,
waiting for network idle before clicking. Together with B1, a mismatch then costs one step
instead of an iteration.

### T4. The caching rule isn't enforced either way (medium)

- `writes.spec.mjs:43-49` checks "pages the app may have cached" after a write, but uses
  `page.goto`, which throws away an SPA's in-memory cache. A TanStack Query app with
  `staleTime: Infinity` passes while breaking "every page must show the change". Navigate
  by clicking the app's links instead.
- The spec allows runtime caching with no time limit. A server cache that never expires
  passes, and `warm()` then serves it with zero API calls. The gain is about 30 ms a call, so this is
  small, but the spec should either set a maximum staleness or say unbounded is fine.

### T5. Smaller test and spec issues

- `layout.spec.mjs:55` accepts any status below 400 for an unknown Host, so a redirect to a fixed
  host passes. Suspicion: Angular SSR's `allowedHosts` may fall back to client rendering with
  a 200. Such an app would pass and then be measured as client-rendered. A cheap guard: in
  `measure.mjs`, record whether the HTML served through Caddy contains the `h1` text. That also
  records each app's real rendering strategy for the report, which M3 needs anyway.
- `getByText('Page 1 of 3', { exact: true })` (`lists.spec.mjs:32, 100, 228`) fails
  `<nav>Page 1 of 3 <a>Next page</a></nav>`, which is a fair reading of the spec. Use `phrase()`.
- `SPEC.md:273`, "from the current year back to 2016". The test uses the data's `today` (2026).
  An app using `new Date()` passes now and fails from 2027-01-01. Say "the year of the data's
  current date".
- `textOf()` reads `innerText`, which skips shadow roots. The README documents this for pokedex
  only. Lit + Vite apps will put text in shadow DOM by default, so expect their agents to
  spend tokens switching to light DOM, and say so in the README.
- Fragile indexes: `definition().nth(5)`, `.nth(2)` (`writes.spec.mjs:68, 47`), and `row.nth(1)`
  having exactly one `img`.
- The gold app serves CSS with `Cache-Control: no-cache` and no validator, so every hard
  navigation refetches it. It isn't measured, but its 1.3 s click shouldn't be quoted as an
  MPA baseline. More generally, MPA click times will depend on each framework's default
  cache headers for static files. That's legitimate, and the report should say so.

## API and data

The data is reproducible: rebuilding under two time zones and a Turkish locale gave a
byte-identical `dex.sqlite`. The server never reads the clock, every API start copies the
database, so writes don't leak between runs, and `LATENCY_MS` applies to every `/api`
request. The export doesn't leak `gold/` or `api-tests/`. `openapi.json` matches its
generator byte for byte.

Issues:

- **Server time isn't "about 30 ms" everywhere.** `/api/meta` takes 14 to 16 ms on top of
  the latency, because `SELECT DISTINCT method FROM catch` scans all 71,859 catches. `/api/games` and
  `/api/stats/completion-by-game` take 17 to 19 ms because of `COUNT(DISTINCT …)` joins. The API is
  synchronous (`DatabaseSync`), so the overview's 4 parallel calls queue to about 35 ms. Fair to everyone,
  but it adds noise. Compute the method lists once at startup. An `EXISTS` rewrite of the
  completion count gives identical output in 2.1 ms instead of 16.5.
- `POST /api/trades` accepts `2026-02-30` (`Date.parse` rolls it over). Malformed
  percent-encoding (`/api/species/%E0%A4%A`, `/media/%E0`) returns 500. An unknown `friend` or
  `method` filter returns 200 and an empty list, while an unknown `game` returns 400.
- A failed insert inside `POST /api/trades` would leave the transaction open, and every later
  POST would fail. Suspected; couldn't trigger it.
- The API sends no `Access-Control-Max-Age`. An SPA that sets `Content-Type: application/json`
  on GETs pays a throttled preflight per URL. That's realistic, but worth a line in the spec.
- `node --test scenarios/dex-tracker/api-tests/`, as documented in the README, finds no tests on Node
  24.22.1. `node --test scenarios/dex-tracker/api-tests/*.test.mjs` runs all 13, and they pass.
- In `api.test.mjs`, marking the common shapes `_partial` turns off the extra-field check for
  them everywhere, and after a POST only `/me`, `/trades` and `/activity` are re-checked.

API calls each measured page needs, and how many sequential rounds:

| Step | Calls | Rounds |
| --- | --- | --- |
| `/` | `me`, `stats/completion-by-game`, `stats/catches-by-month`, `activity` | 1 |
| `/needs` | `needs`, plus `meta` unless generations are hard-coded | 1, then 50 sprites |
| `/pokemon/ivysaur` | `species/ivysaur`, `species/ivysaur/catches` | 1, then the artwork |
| `/trades` | `trades`, `meta`, `friends` page 1, `friends` page 2 | 2 (see M7) |
| `/trades?page=2` | `trades?page=2`, plus the filter lists if refetched | 1 to 2 |

## The new Vite entries

- The labels "React with Vite", "Preact with Vite" and "Lit with Vite" don't say client-side,
  and the spec leaves the rendering strategy open. An agent can pick React Router's framework
  mode, which duplicates `react-router`, or Vite SSR. That's consistent with the
  vibe-coding rule. Just don't describe them as "the SPA entries" in the write-up unless the
  apps turn out to be SPAs. T5's check that records whether the served HTML contains the `h1`
  settles it per iteration.
- The likely `npm start` is `vite preview`, which serves files through sirv with ETags and
  `Last-Modified` but no `Cache-Control`. Chrome then caches by heuristic, 10% of the time
  since the build. That's fine within a 15 s session. Worth knowing if a number looks odd.
- T1 and the shadow-DOM note in T5 will hit these three harder than anything else in the run.

## Docs

- README line 10 says `--frameworks=all --iterations=5` reproduces the published v1 results,
  but `all` now includes the three Vite entries, which v1 didn't have.
- README "What happens in a run" still names the images `pokedex-base`, `pokedex-agent` and
  `pokedex-measure`. They're now `<scenario>-base` and so on. `Containerfile.measure`'s default
  and the comment at `run.mjs:251` have the same leftover.
- `serve.sh`'s comment "default 30, as in the tests and measurements" isn't true for pokedex,
  which runs at 0.
- The README's "it does so the same way for every app" about DevTools throttling (see M2).

## Order of work

Before the run, roughly in order of value for the effort:

1. B1: catch errors per session and always write `results.json`.
